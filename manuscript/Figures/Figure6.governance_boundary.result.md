# Figure 6：一次可观察的治理失效与由此产生的边界重设计

> 状态：**持续更新中的 result 草稿（非投稿形式）**。当前 Manuscript Phase 0，PaperSpine
> intake 已完成、research 尚未放行。本文件属 Figure spine 规划与证据记录，**不构成**
> `confirmed_contribution`，也不构成任何 Phase 放行。

## 为什么做

一篇 design-and-implementation / systems paper 最容易受到的质疑，不是「没有 E5 外部实证
所以没资格写」，而是**用一组精美的架构图把一个只有软件实现与内部验证的系统，包装成已经
证明研发效用的 biotechnology platform**。前三张图（抽象、模型、实现）全部是系统的自我
描述；如果评价部分也只有「测试通过」「模块达 1.0.0」，整篇论文就没有任何一处允许读者
看到系统**失败**的样子。

Figure 6 处理的正是这个缺口。它不展示 StelligenOS 的能力，而展示一次在真实运行中发生、
有完整审计轨迹的治理失效，以及系统对该失效的架构响应。对 systems paper 而言，一个被
记录下来的 failure mode 与随之而来的边界修订，其方法学价值高于又一张成功路径图。

本图同时服务于 `MANUSCRIPT_CHARTER.zh-CN.md` §3 的第 3 条允许主张（治理可追溯性），
并为 §4 的禁止主张提供自我约束的证据：系统自己记录了它做不到什么。

## 做了什么

分析对象是关联仓库 `AIDD_ADC_design` 中的事件 INC-2026-001 及其两轮处置。全部材料为
E2（软件验证：扫描器、hook、CI、boundary checks）与 E3（审计轨迹：PR、handoff、worklog、
review records），**不涉及任何 E4 候选数据或 E5 外部实证**。

1. **事件复盘**：确认根因属于哪一类错误——是检测能力不足，还是安全边界设计错误。
2. **控制交付复盘**：统计第一轮处置（防泄漏控制）的审核过程本身，包括阻断数量与其中
   由前一轮修复自身引入的比例。
3. **边界重设计复盘**：记录第二轮处置（仓库分离）的设计决定、审核结论与**授权边界**。
4. **事实状态核验**：区分「方案已获批准」与「远端操作已执行」，确保图中状态不被夸大。

不做的事：不以此主张重设计能防止未来事件；不把阻断计数转换为缺陷率或安全性估计；不把
任何治理记录当作 accepted biological result；不在本公开仓库写入事件的精确定位信息
（受控内部登记中的 blob 标识、行号与内容摘要一律不进入本文件，理由见下）。

## 结果

### 根因是安全边界设计错误，而非检测能力不足

事件的表层描述是「序列材料出现在公开仓库」，但该材料是在仓库处于 private 状态时提交的，
且位于一条从未合并的分支上。真正的机制是：**可公开的治理证据与必须保密的研发证据被放在
同一个 Git 安全域**，一次 private → public 的 visibility 变更把整个域一次性搬过了边界。

直接触发同样属于边界性质：外部审核工具无法读取 private 仓库，为完成一轮审核而把仓库
转为 public。也就是说，一个依赖公开仓库才能完成外部审核的治理系统，不能同时承载尚未
公开的研发资产——这两项要求在同一个安全域内不可共存。

这一判定在复盘中被一项独立核验修正过：最初误把仓库 API 的 `createdAt` 读作「转为 public
的时间」，导致暴露窗口被高估数个量级，并据此推导出错误的司法辖区期限。独立核验仓库记录
后更正。该更正本身构成证据：**依赖单一元数据字段推断安全状态是不可靠的**。

### 控制交付：七轮审核、17 项阻断，其中 6 项由前一轮修复自身引入

第一轮处置交付了一组防泄漏控制：序列扫描器、pre-commit 与 pre-push hook、CI 作业，以及
visibility 变更门禁。交付过程本身产生了可统计的审计轨迹：**七轮外部审核，累计 17 项
阻断，其中 6 项由紧接其前的修复自身引入**，且全部 17 项在修复前于本地复现。

这一统计**描述的是一次内部修复过程，不构成对缺陷率、残余风险或未来安全性的定量估计**。
它支持的唯一结论是方法学性质的：检测器与审核流程自身也需要接受反复验证，而不是一经交付
即可信赖。

过程中出现的若干失效模式对 systems paper 有直接意义，因为它们都属于「检查通过了，但是
因为错误的原因」：

- 范围扫描检查最终产物树而非对象，使「先添加再删除」的路径不可见；
- visibility 门禁只扫描 ref 顶端，而事件材料恰好在一条未合并分支上；
- 公开的事件记录文档本身泄漏了精确定位信息——为记录披露而发布定位器会扩大该披露；
- 扫描器在 3 处等长分块上的规则对普通英文散文误报，一度阻断了交付自身的提交。

控制的真实效力被逐项写明：只有 pre-push 与 visibility 门禁能阻止**首次**披露；CI 在内容
已到达远端之后才运行；服务端 custom-pattern push protection 需要组织级订阅，本项目
**不具备**，不得在任何地方记为已部署控制。残余漏检（转义引号、非均匀切分、编码序列、
跨文件切分、Web 编辑器绕过 hook）被显式列出并接受，而非声称已关闭。

### 边界重设计：扫描器是网，不是边界

第二轮处置的核心判断是：七轮审核与 17 项阻断已经充分说明，**把网织得更密不改变它只是
网**。因此第二轮不再加强检测，而是重设边界——把仓库拆分为「公开治理」与「私有研发」
两个独立安全域，使未经授权的研发资产在技术架构上没有一条自然路径可以进入公开 Git。

扫描器在新架构中的角色由「边界」**降级**为「回归保护」：它在人为失误时兜底，不作为资产
保密的依据。

该设计明确拒绝了改写历史的选项：重写会使审计文档、受控内部登记与既往 PR 引用的全部
commit 标识失效，摧毁这些审核刚刚建立的溯源链，而且**仍然收不回已发生的披露**。代价是
公开侧没有早期开发史——这被判定为可接受，因为公开侧的价值在于当前治理状态与审核记录。

设计同时如实记录了分离的代价：私有化后，外部审核工具无法再读取研发侧内容。由此审核分为
两级且结论不得混同——Governance Gate 只能判定范围合规、逻辑一致、证据等级与对外宣称
边界；Technical Gate 的合规通道尚未确定，状态一律记为 `not yet independently verified`。
另记录：把 private diff 粘贴进聊天**不是**自动安全的替代方案，它绕开 GitHub 可见性但仍
把内容传给外部服务。

### 审核过程中被独立发现的三项阻断

分离方案的外部审核第一轮返回 `REQUEST_CHANGES`，三项阻断均属实施细节，且都属于同一类
错误——**控制在某一步成立，却没有贯穿到最后一道门禁**：

1. 文件白名单在起始步骤成立，但后续步骤改用「暂存目录内现有全部文件」，而公开前的门禁
   只依赖序列扫描器；该扫描器按设计只检测序列，**不能证明文件树仍等于批准的白名单**，
   一个不含序列但不该公开的文件可以通过。
2. 完成记录文件会使公开仓库的文件数超出验收标准所规定的集合，在写下该文件的瞬间破坏
   该标准。
3. 把「外部审核批准方案」读作「可以变更仓库访问权限」，而既有政策要求 visibility 变更
   经人类负责人明确批准，agent 规则更直接禁止 agent 更改 visibility。

第 3 项与事件根因属同一类错误：**把一种授权当作另一种**。三项在同一 PR 内通过最小修订
关闭，第二轮返回 `APPROVE`（3/3 CLOSED）。

### 事实状态：方案已批准，执行尚未完成

批准的范围是**分离的设计、实施计划与文档边界**，**不包含**远端操作的执行授权。创建新
仓库、初始推送，以及两次 visibility 变更，均需负责人逐项、逐仓库明确确认，且一次确认
不可沿用至另一次。

因此本图当前只能标注为 `approved separation design / execution pending verification`，
**不得**绘制为 "completed and validated separation"。

### 证据来源

全部为公开可查的脱敏材料：关联仓库的披露政策、公开事件登记、仓库分离设计与实施计划，
以及 PR #6（控制交付）与 PR #7（边界重设计）的审核记录。

含精确定位信息的受控内部登记**不在本仓库，也不进入本文件**：为记录一次披露而发布精确
定位器会扩大该披露，并为受限材料建立可检索索引。这既是事件处置中的一项结论，也是本
result 自身遵守的规则。

## 结论

Figure 6 支持三项结论，且仅支持这三项：

1. 发生过一次有完整审计轨迹的治理失效，其根因是安全边界设计错误——治理与研发共用同一
   Git 安全域——而非检测能力不足。
2. 该失效被审计、被公开登记，并驱动了两轮设计响应：先交付防泄漏控制，再重设安全域边界
   并将扫描器从「边界」降级为「回归保护」。
3. 系统对自身控制的效力作出了**降级而非抬高**的陈述：逐项写明哪些控制能阻止首次披露、
   哪些不能、哪些不具备，并显式列出接受的残余漏检。

**不支持**的结论：重设计已被证明能防止未来事件；17 项阻断可换算为缺陷率或安全性估计；
分离已执行完成；治理记录等价于科学或生物学验证。

据此，Figure 6 定位为 **negative governance case study**，置于 Evaluation 并与
Discussion / Limitations 交叉引用；它是 limitation 证据，不是安全能力的成功证明。

## 讨论

把这条材料放进主图，与把它藏进 Limitations，是两种不同的论文伦理立场。藏起来可以让
Evaluation 看上去更干净，但也就取消了读者判断系统边界的能力——而「边界清晰」恰恰是本文
主张的设计性质之一。一个声称以可审计性为核心贡献的系统，若在自己的论文里隐去唯一一次
被审计出来的失效，这个主张就自相矛盾。

反方向的风险同样真实：把一次失效的处置写成「我们因此更安全了」属于过度抬高。这正是
本图把所有数字都限定为过程描述、把所有控制效力都写成降级陈述的原因。**七轮 17 项**
这个数字最容易被误读为质量指标；它只能说明修复过程是迭代的，其中 6 项由前一轮修复自身
引入这一点，恰恰是反对「控制已趋于完善」这一读法的证据。

对 systems paper 的一般性意义在于：**因错误原因通过的检查比没有检查更糟**。本案例中
反复出现的失效模式——扫描错误的对象、只扫描 ref 顶端、在非 git 目录中把 fail-closed
的退出码读作成功、在记录披露时发布定位器——都不是「控制缺失」，而是「控制看起来在工作」。
这类失效无法靠增加控制数量解决，只能靠边界设计与对每一项检查的语义核验。

一个仍然开放的张力：本图依赖的全部证据都由被评价的系统自身生产（E2/E3）。这是当前证据
结构的固有限制，Figure 4 与 Figure 6 共同受其影响。外部独立复现需要 E5，当前不存在，
也不得推断。
